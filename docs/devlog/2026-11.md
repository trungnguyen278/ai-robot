## 2026-11-02 — The Pi 5 on Ubuntu, and the face's kiosk

**Done:** The Pi 5 runs Ubuntu Server 26.04.1 ([ADR-0017](../decisions/0017-ros-2.md)) and shows the robot's face.
- Flashed from the PC with Raspberry Pi Imager and cloud-init. It boots kernel 7.0.0-1020-raspi through `piboot-try`'s A/B boot.
- cloud-init's seed on the boot partition held the Wi-Fi key and the password hash. cloud-init is now disabled and the seed removed, in that order: removing the seed first would make the next boot a new instance, with new SSH host keys.
- The robot software runs in a virtual environment (Python 3.14.4), and `ai-robot --profile desktop` runs as a systemd service.
- The kiosk of [ADR-0006](../decisions/0006-screen-renderer.md) is Ubuntu Frame with the Chromium snap (156) in its daemon mode, on `http://127.0.0.1:8770/`. Frame tracks 24/stable (Mir 2.26), since track 26 has no stable release yet.
  - Chromium runs with `--no-first-run`: without it, a fresh profile waits on the first-run dialog and never loads the page.
  - Frame's cursor is off (`cursor=null`): a keyboard's extra mouse interface made Mir draw one.
  - The `cups` snap that Chromium pulls in served printing on every network interface, so its services are disabled.
- The Wi-Fi driver now takes the options Raspberry Pi OS ships "for stability", which Ubuntu does not: `roamoff=1 feature_disable=0x282000`, in `/etc/modprobe.d/` ([firmware-nonfree commit 348a96721f](https://github.com/RPi-Distro/firmware-nonfree/commit/348a96721f), 2026-07-10). With them the Pi joins 5 GHz directly, as it did under Raspberry Pi OS.
- Local access while the kiosk holds the screen:
  - Ctrl+Alt+F1 switches to a text login on tty1, small at 2560 × 1440. Frame runs on tty4, and switching back resumes the kiosk (checked with `chvt`);
  - Ubuntu's serial console is on UART0, GPIO 14/15.

**Decisions:** None. The owner chose to measure the face once the 7" display arrives, and not to report the snapd bug below yet.

**Problems / unfinished:**
- **No GPU for the Chromium snap on a Pi 5.**
  - The cause is in snapd. Its `opengl` interface lets a snap read the PCI files under `platform/{soc,scb}/*.pcie/` (Pi 4) but not under the Pi 5's `platform/axi/*.pcie/`. [`opengl.go`](https://github.com/canonical/snapd/blob/master/interfaces/builtin/opengl.go) was unchanged on master on 2026-11-02.
  - In Chromium's GPU process, libpci cannot read the PCIe root port's `device` file. It prints `pcilib: Cannot open …` and the process exits.
  - After three tries, Chromium draws in software: about 20 frames a second at 2560 × 1440 on a test monitor.
  - The fix belongs in snapd.
- **The Wi-Fi dropped for hours.**
  - The home router steers clients from 2.4 to 5 GHz (802.11v).
  - networkd and wpa_supplicant restarted together while the Pi was on 5 GHz: unattended-upgrades was upgrading systemd. From then on, every join or roam on 5 GHz timed out until a reboot, and after enough failures the router refused 2.4 GHz too.
  - Two earlier identical restarts were harmless.
  - Not the wpa_supplicant 2.11 bug with brcmfmac: 26.04's package carries its revert ([LP #2124258](https://bugs.launchpad.net/ubuntu/+source/wpa/+bug/2124258)).
  - With Raspberry Pi OS's options, the same restart five times in a row: each time the Pi was back on 5 GHz within 3 to 23 s, directly or through the router's steering. That proves little alone, since the failure hit only one restart in three; the coming unattended upgrades are the real test.
- **`ai-robot.local` stopped resolving after a roam from 2.4 to 5 GHz.**
  - avahi logged a host name conflict and renamed the Pi `ai-robot-2.local`. Restarting avahi restores the name.
  - This is [avahi#117](https://github.com/avahi/avahi/issues/117), open since 2017. After a link event, avahi withdraws and re-registers its records while IPv6 addresses change. Its own stale probe comes back through multicast loopback, avahi takes it for another host, and it renames itself at once instead of probing again as RFC 6762 §8.2 asks.
  - The fix, [avahi#982](https://github.com/avahi/avahi/pull/982), is a draft. It reports that setting `publish-aaaa-on-ipv4=no` and `publish-a-on-ipv6=no` stops the renames.
  - Either way, the product should not depend on a fixed mDNS host name.
- **A test monitor toggled HDMI hot-plug about 17 times a second.** This kept Frame from compositing: a black screen with a cursor. `vc4.force_hotplug` stops it, set at run time only. Cable or kernel: not known.
- Questions for the product, not decided:
  - Whether release builds keep VT switching and a console login: anyone with a keyboard gets a login prompt.
  - Moving the service console to the 3-pin debug connector (UART10), since GPIO 14/15 is the UART planned for the body controller.
  - The robot's connection watchdog, and how OS updates may restart services.
  - Where the Pi's set-up lives: the scripts and settings above are not in the repository yet.

**Next:** Watch the Wi-Fi through the next unattended upgrades. With the 7" display: the ADR-0006 measurements, once Chromium can use the GPU.

## 2026-11-03 — Schema checks: where patterns end, and no values in problems

**Done:** two fixes to `core/data.py`'s `Schema`, which a review of ai-cloud's homes ([ai-cloud#20](https://github.com/trungnguyen278/ai-cloud/pull/20)) found there first, and a third they led to.
- **A pattern's final `$`** is read as ECMA-262 reads it, whose regular expressions JSON Schema's patterns are. Python's `$` also matches before a last newline, so `"x\n"` passed every pattern of the cloud link and of set-up. A test keeps both protocols' patterns to what Python and ECMA-262 read alike: their only `$` ends them, and none uses `\d`, `\w` or `\s`, which Python reads otherwise on text beyond ASCII.
- **A problem no longer quotes the value.** jsonschema's messages do (`'…' is too long`), and the robot logs the problem of a message it refuses. A set-up `join` whose Wi-Fi password had over 128 characters put the password in the log, at INFO; a token in a cloud message could do the same. A problem now names where and the rule broken, as ai-cloud's do. The errors a capability sends the cloud keep the rule, such as an `enum`'s values, without the value.
- **A set-up error's text** is cut to the 256 characters that the protocol allows, as the cloud link's already was. A long refusal, such as the one above, made an error that broke set-up's own schema.

**Problems / unfinished:** GitHub's `ubuntu-latest` became Ubuntu 26.04, whose PortAudio starts only when a sound server answers, as [ADR-0017](../decisions/0017-ros-2.md) foresaw. Every pull request touching `software/` failed, until the tests ran on Ubuntu 26.04, pinned, with PipeWire ([#43](https://github.com/trungnguyen278/ai-robot/pull/43)). On the robot, PipeWire must likewise run before the nodes that use sound.

**Next:** ai-platform's ADR-0010 and the app API 1.2, on patterns that every engine reads alike.

## 2026-11-13 — Set-up 2.1

**Done:** the robot speaks [set-up 2.1](https://github.com/trungnguyen278/ai-platform/blob/main/protocols/setup/README.md), with `platform/` pinned at `setup/v2.1`. That commit also publishes the cloud link 3.1, which the robot does not speak yet.
- **Errors say what they answer.** `version` replies to the app's `hello` (1), and `code` to its `confirm` (3). Only an error about a message that cannot be read has no `reply_to`: one that is not JSON, not an object or without a `seq`.
- **JSON that every side can hold** ([ai-platform ADR-0014](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0014-json-every-side-can-hold.md)). `core/data.py`'s `read_json` reads the app's messages. It refuses a U+0000, a lone surrogate, nesting deeper than 64, NaN and a number past a double. It counts the nesting before it parses, so the answer does not depend on where the parser gives up. Every set-up example passes it.
- **One app at a time.** The session belongs to the first app whose `hello` comes. Another app's `hello` gets `busy`, numbered 1 and replying to 1, sent to that app only, and the robot then drops it; the session goes on. An app that connects once set-up has closed gets no message, and is dropped.
- **Fragments.** A fragment without bytes adds nothing. The robot holds a message's announced length at most, and refuses a fragment at the first byte past it. Its own fragments hold 512 bytes at most, the longest attribute value (Bluetooth Core, Vol 3, Part F, 3.2.9), which BlueZ 5.85 enforces as `BT_ATT_MAX_VALUE_LEN`. At an MTU over 515, BlueZ cut the robot's indications: it truncates a `Value` to 512 bytes.
- **Network names.** A name holding a NUL byte goes as `ssid_hex`, since no side holds a U+0000 in a string. `networks` leaves out hidden networks, as NetworkManager counts them: a name that is empty, a single space, or all NUL bytes (`_nm_utils_is_empty_ssid_arr`, `src/libnm-glib-aux/nm-shared-utils.c`, read 2026-11-13). hostapd hides a network behind NUL bytes of the name's length (`ignore_broadcast_ssid=2`, `hostapd/hostapd.conf`).

**Decisions:** delegated.
- **Whose session it is.** It belongs to the first app whose `hello` comes, not the first to connect. The protocol has `busy` answer a second app's `hello`, but leaves open which app is second when both connect before either speaks. Matter's CASE server does the same: a `Sigma1` that comes while a handshake runs gets a Busy status report (connectedhomeip, `src/protocols/secure_channel/CASEServer.cpp`, `OnMessageReceived`, master `f09331bd`, read 2026-11-13). An app that connects and says nothing is dropped after `idle`, as a session is.
- **512 bytes.** The robot caps its fragments at 512 bytes as well as at the MTU minus 3.

**Problems / unfinished:**
- **`busy` on the radio.** The `bluez` adapter still indicates through the characteristic's `Value`, which BlueZ sends to every app that enabled indications. `busy` therefore reaches only its app on the simulated link. It does so over Bluetooth only once the adapter gives each app its own channel, through `AcquireNotify` (the next pull request).
- **The protocol says "the ATT MTU minus 3 bytes".** BlueZ 5.85 refuses a longer write than 512 bytes (`check_length` in `src/shared/gatt-server.c`). An app at an MTU of 517 that writes 514-byte fragments would be refused. ai-platform should add the 512-byte bound.

**Next:** the `bluez` adapter on `AcquireNotify`, then a session on the Pi with two phones.

## 2026-11-13 — The BlueZ link on `AcquireNotify`

**Done:** the `bluez` adapter gives each app its own channel for set-up's indications. What the robot sends one app, such as `busy`, reaches that app only, where the characteristic's `Value` reached every app that had enabled indications: "`busy` on the radio" above.
- **A channel per app.** The Answer characteristic has `NotifyAcquired`. When an app enables indications, BlueZ 5.85 calls `AcquireNotify` with the app's device and MTU (`ccc_write_cb` and `append_options`, `src/gatt-database.c`). The robot answers with one end of a `SOCK_SEQPACKET` socket pair. BlueZ indicates each packet it reads from that end to that app alone, 512 bytes at most, and writes one byte, 0x01, for each confirmation (`sock_io_read`, `sock_io_write`). The robot waits for that byte before the next fragment, as it waited for `Confirm`.
- **Closing.** BlueZ shuts its end down when the app disables indications or disconnects (`client_io_free`, `att_disconnect_cb`). An app whose channel closes in the middle of a message is dropped. The robot closes an app's channel itself when it drops the app or stops, even when BlueZ fails to disconnect the app.
- **`confirm_timeout`** bounds the wait for an app's channel as well as for each confirmation.

**Decisions:** delegated.
- **A socket pair per app,** as bluetoothctl's own GATT server makes it (`create_sock`, `client/gatt.c`): `SOCK_SEQPACKET` and non-blocking, the robot's copy of BlueZ's end closed once the reply is sent. dbus-fast 5.2.0 passes descriptors only on a bus made with `negotiate_unix_fd=True`, and sends one when it writes the message out, keeping no copy (read 2026-11-13).
- **The robot waits for a channel,** up to `confirm_timeout`: `AcquireNotify` "may be delayed in order to have the exchange MTU completed" (`doc/org.bluez.GattCharacteristic.rst`).
- **One message at a time for each app,** so an app that does not confirm holds up only its own messages.
- **A refused `AcquireNotify` is `org.bluez.Error.Failed`:** one for a device of another controller, or without options. After any other error BlueZ falls back on `StartNotify` (`acquire_notify_reply`), which the robot no longer has.
- **No check of the caller,** as for `WriteValue`: BlueZ's D-Bus policy lets only root send to `org.bluez.GattCharacteristic1` (`src/bluetooth.conf`).

All of BlueZ is read at its tag 5.85, Ubuntu 26.04's, on 2026-11-13.

**Problems / unfinished:** the channel is written against BlueZ's source and tested against the fake BlueZ only. Its pull request waits for a session on the Pi: one phone, a second phone that gets `busy`, an MTU of 517, indications disabled and enabled again, and a phone that disconnects in the middle of a message.

**Next:** that session on the Pi.

## 2026-11-13 — A patched BlueZ

- **`tools/pi/patched-bluez.sh`** builds it, with the patch kept in `tools/third_party/bluez/`. On the Pi, as `pi`, the build took 12 minutes. Ubuntu's packaging does not run BlueZ's own tests, so step 7 on the Pi is the build's test.
- **Step 7 passed in full** on the build, `5.85-4ubuntu0.4+local1`, installed and held on the Pi (21:19–21:21).
  - The phone's `hello` got `busy`, numbered 1 and replying to 1, and the robot dropped the phone.

**Decisions (delegated):**

- **The version suffix, `+local1`,** sorts above the version built from and below Ubuntu's next, as `dpkg --compare-versions` confirmed on the Pi.
  - `check` compares versions exactly, so it still notices an Ubuntu rebuild such as `…build1`, which sorts below the suffix.
- **The patch is upstream's,** as git.kernel.org serves it, byte for byte. It goes into `debian/patches` and `dpkg-source` applies it, so the build's source carries it.
- **The build stops** when a patch already applies in reverse: Ubuntu has it, and the patch is dropped. It also stops when a patch applies neither way.
- **No root:** the script prints the root commands instead of running them.
- **`check` exits with 1** when the installed build is not Ubuntu's newest, or not held.
- **The build's changelog entry** names `Local build <local-build@localhost>` unless `DEBFULLNAME` and `DEBEMAIL` are set, so no person's or machine's name lands in the package.
- **Where things go:**
  - the Pi's set-up scripts go in `tools/pi/`, as `tools/README.md` had planned;
  - third-party code goes in `tools/third_party/`, as CONTRIBUTING says for every component.

**Problems / unfinished:**
- **Security fixes wait.** On a Pi upgraded with apt, Ubuntu's security fixes to `bluez` now wait for a rebuild, so `check` has to be run.
- **No re-registration.** The robot does not register again when `bluetoothd` restarts, and installing a `bluez` restarts it (the package's `postinst`). The robot's software, when it runs the `pi` profile, is therefore restarted after.
- **Found by the second review of #45 and this pull request,** neither blocking:
  - **Any local user can end a set-up session.** The adapter acts on a `PropertiesChanged` signal without checking its sender. The match rule filters only broadcast signals, and the system bus's policy lets any connection send a signal to one recipient. A probe ended a session this way from an unrelated connection. The adapter had this gap before #45.
  - **A bonded phone that reconnects** while set-up is still open gets no channel. BlueZ keeps a bonded device's CCC value between connections, and calls `AcquireNotify` only when the value changes (`gatt_ccc_write_cb`, `src/gatt-database.c`). The robot drops that phone after `confirm_timeout`. Set-up does not ask for Bluetooth's pairing ([ADR-0015](../decisions/0015-set-up.md)). Not tried on the radio.

## 2026-11-14 — BlueZ restarts, and signals from their senders

**Done:**
- **The `bluez` link recovers when `bluetoothd` restarts,** as installing or upgrading `bluez` makes it do ([ADR-0020](../decisions/0020-patched-bluez.md)). It follows `org.bluez`'s owner on the bus (`NameOwnerChanged`).
  - When BlueZ goes, set-up's apps are dropped and their channels closed. The service stays open, and the robot logs a warning.
  - When BlueZ comes back, the robot lists its objects (`GetManagedObjects`), and registers its service and advertisement again as soon as the controller offers `GattManager1` and `LEAdvertisingManager1`.
  - The same holds when the controller goes away and comes back (`InterfacesRemoved` and `InterfacesAdded`). A controller powered off and on needs nothing.
- **Only the service's signals count.** The `bluez` and `networkmanager` adapters act on a signal only when its sender is the service's current unique name (`Owner`, `adapters/dbus.py`). A match rule's `sender` is no such check: the bus delivers a signal sent to one connection whatever rules that connection asked for (the D-Bus specification 0.43), and the system bus lets any connection send signals (dbus 1.16.2, `bus/system.conf.in`). The review's probe that ended a session from another connection no longer does.
- **`platform/` is pinned at `setup/v2.2`,** and the robot says `"2.2"`. 2.2 asks nothing the robot did not already do: fragments of 512 bytes at most, `ssid_hex` for names that hold NUL, hidden networks left out of the list, and joining a network that is not listed.

**Decisions:** delegated.
- **Follow the owner, not restart with BlueZ** (no `PartOf=bluetooth.service`), as BlueZ's own D-Bus client does: `gdbus/client.c` lists the objects when the service appears (`service_connect`) and drops its proxies when it goes (`service_disconnect`); `gdbus/watch.c` drops a signal whose sender is not the name's owner.
- **Register when the managers appear, not when the name does:** BlueZ takes its name before the controller's object exists, and adds `LEAdvertisingManager1` later than `GattManager1`, once the controller has told its features (`read_adv_features_callback`, `src/advertising.c`). PipeWire 1.4.9 waits likewise for the adapter's interfaces before it registers (`spa/plugins/bluez5/bluez5-dbus.c`).
- **Power off and on needs nothing.** BlueZ 5.85 keeps both registrations while the controller is off (no power handling in `src/advertising.c` or `src/gatt-database.c`). The kernel keeps the advertisement and programs it again when the controller is powered (`hci_dev_close_sync`, `hci_powered_update_adv_sync`, Linux 6.17), and mgmt's Add Advertising "can be used when the controller is not powered" (`doc/mgmt.rst`). Apps leave as before, through `Device1.Connected`.
- **What the robot was asked is kept apart from what BlueZ holds,** so that a `start`, `advertise` or `stop` while BlueZ is away holds once it is back.
- **`start` still fails** while BlueZ or the controller's managers are missing, and leaves nothing registered when it fails. The person sees why.
- **Races:** a listing during which BlueZ or its managers changed is taken again; a registration that BlueZ lost as it answered is made again.

Sources were read on 2026-11-13 and 2026-11-14: BlueZ at its tag 5.85, PipeWire at 1.4.9, Linux at v6.17, dbus at 1.16.2.

**Problems / unfinished:** the restart is tested against the fake BlueZ and a private bus only. On the Pi it needs `systemctl restart bluetooth` while set-up is open.

**Next:**
- that check on the Pi;
- NetworkManager restarts: the adapter hears the new NetworkManager, but keeps the Wi-Fi device's object path it learned when it opened, which the new one may number otherwise.

## 2026-11-14 — The robot sleeps and wakes

**Done:**
- **The robot sleeps** after "Sleep after" minutes with nothing going on: 1, 2, 5, 10 or 30, or never, with 5 as shipped (`screen.sleep_after`, in the settings' Display section). Its face grows sleepy and closes its eyes, and then the kiosk turns the screen off ([ADR-0021](../decisions/0021-sleep-and-wake.md)).
  - Nothing counts during a conversation, while a scene that keeps it awake shows (set-up's while set-up is open, and the vocabulary's `keeps_awake` scenes, the timer), or while a panel is open.
- **One way to wake:** every wake source publishes `WakeUp(source, reason)`.
  - The screen publishes `touch` for each tap, hold and panel action, and `event` when something starts while the robot sleeps. The voice module publishes `wake_word`.
  - The tap that wakes the robot does nothing else.
- **The screen protocol** stays at version 1: `state` gains an optional `asleep`, and the vocabulary's scenes an optional `keeps_awake`.
- **The renderer** holds a Screen Wake Lock while the robot is awake (`ui/src/sleep.js`). Asleep, it shows `sleepy`, then the new `asleep` face, and then lets the lock go. It hides the scene and the panel.
- **A dark screen is lit** through a new port, `display_power`. Its `helper` adapter asks `ai-robot-wake`, which presses `KEY_WAKEUP` on a uinput keyboard that has no other key (`adapters/wake/helper.py`, standard library only). The robot also lights the screen when a page connects while it is awake.
- **The kiosk's set-up is in `tools/pi/`:** `kiosk.sh install PROFILE DIR` and `kiosk.sh check PROFILE`, with the files of `tools/pi/kiosk/`.
  - It sets Frame's config, with `add-wayland-extensions=zwp_idle_inhibit_manager_v1`, and Chromium's drop-in.
  - It installs the robot's unit, the helper's socket and unit, and the uinput rule.
- **Checked on the Pi** on 2026-11-14:
  - the wake lock and the key (the coordinator's tests 1 and 2, in the ADR);
  - the helper's keyboard lit the dark screen, run as `pi` and under the unit's system call filter;
  - `systemd-analyze verify` passes on the helper's units, and `systemd-analyze security` scores the service 0.7;
  - `kiosk.sh check` reads Frame's config and Chromium's page correctly;
  - the full suite passes in Docker. On the Pi it passes but for the tests that need a sound server,
    a LiveKit server or the port of the running robot, which an ssh session there does not have.

**Decisions:** the behaviour and the helper are the owner's (2026-11-14). The rest was delegated:
- **The screen module owns sleep,** because it knows what shows and what holds it.
- **The timings:**
  - Frame's `idle-timeout` is 15 s, the time from closed eyes to a dark screen;
  - the renderer shows 3 s of a sleepy face, then 2 s of closed eyes, before it lets the lock go.
- **The waking tap only wakes,** as a tap wakes Nest Hub's screen ("Wake up your screen: Tap it", support.google.com/googlehome/answer/9137285). The face it lands on was not showing.
- **The robot's user leaves `input` too, not only `uinput`.** Its members can write events into the touch screen's device (`evdev_write` calls `input_inject_event`, Linux's `drivers/input/evdev.c`).
- **The helper's socket** is for the robot's user's own group. A group of its own would add nothing, since that user owns the tree the robot runs from.
- **The helper's program is a copy in `/usr/local/libexec`,** which only root may change.
- **A press that fails ends the helper,** and systemd starts it again with a new keyboard.
- **No `modules-load.d` file:**
  - `kmod-static-nodes` makes `/dev/uinput` at boot (the module's alias `devname:uinput`);
  - udev gives the node its group then (`static_node=`, udev(7));
  - the module loads on the node's first open (`char-major-10-223`).
- **`kiosk.sh` asks for no root,** as `patched-bluez.sh` does: it prints the root commands. `check` reads Frame's own config file and the command line of Chromium's daemon. Neither needs root, as `snap get` does.
- **Chromium stops and starts with Frame (`PartOf=`), and restarts whenever it exits (`Restart=always`).** It exits with status 0 when Frame restarts, which the snap's `Restart=on-failure` left down.

**Problems / unfinished:**
- **The kiosk is not installed on the Pi yet:** that needs root, so the coordinator runs the commands. Then it needs a check by hand:
  - the screen sleeps after 1 minute;
  - a tap wakes it;
  - `snap restart ubuntu-frame` brings Chromium back.
  - The helper's unit, with its dynamic user and device policy, runs only once it is installed.
- **Tools that read the touch screen's device directly,** such as `evtest`, need root once `pi` leaves `input`.
- **A proposal for the owner** is in ADR-0021: offer Mir an output-power protocol upstream, which would let the robot turn the screen off and on without the helper.

**Next:** the Pi steps above. Presence (the camera) and the owner's app will publish `WakeUp` once they exist.
